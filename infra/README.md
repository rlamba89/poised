# infra: Preopsis on AWS (CDK, Python)

The AWS side of Preopsis (plans [F3](../docs/plans/f3-lambda-entrypoints.md) and [F4](../docs/plans/f4-aws-pipeline.md), sessions S06 and S07; S12's sign-in; S17's jobs and messaging).

**A push to `master` on GitHub (`rlamba89/poised`) runs the pipeline:** every test, then a deploy of each environment in [`countries.py`](countries.py), then each one's database migrations and seed, its web app, and the end-to-end journeys against it. Nothing else is needed day to day.

One environment, e.g. `uk-qa`, is:

- **`MessagingStack`** (`poised-<env>-messaging`, S17), only for an entry that really sends (`messaging="send"`, or QA's `qa_test_recipients`), deployed first:
  - **SES:** the sender's identity (until there's a domain, an email address read from SSM `<prefix>/email-from`, so it isn't in the repo; SES emails it a verification link to click once), and the configuration set `poised-<env>`, whose event destination sends bounces, rejects and rendering failures to the delivery topic;
  - **SMS (AWS End User Messaging):** the configuration set `poised-<env>`, with a **protect configuration that allows only the entry's phone country** (every other country `BLOCK`; `sms_countries.py` lists them) and an event destination for undelivered texts; and the entry's `sms_sender_id`, if it names one;
  - **the delivery topic** `poised-<env>-deliveries` (SNS), which both services may publish to.
- **`ApiStack`** (`poised-<env>-api`):
  - the Go API as two Lambda functions, `poised-<env>-staff-api` and `poised-<env>-patient-api` (`provided.al2023`, arm64, 512 MB, logs kept 14 days);
  - **the jobs Lambda** `poised-<env>-jobs` (S17): run by the **EventBridge Scheduler** schedule `poised-<env>-jobs` every `jobs_every_minutes` (5; 15 on QA) to send reminders and mark "not responding" (no retries: the next run comes soon), and by the delivery topic, to record undelivered texts and emails on their episodes (OPS-05);
  - **alarms** (OPS-05), emailed to the budget's address (`/sj/alert-email`) through the topic `poised-<env>-alarms`: `poised-<env>-delivery-failures` (any `DELIVERY_FAILED` line in the three functions' logs: a message AWS refused or didn't deliver) and `poised-<env>-jobs-failed` (a jobs run failed). **AWS emails the address a subscription confirmation once: click it**, or no alarm email arrives;
  - an API Gateway **HTTP API**: `ANY /api/p/{proxy+}` → patient-api, `ANY /api/{proxy+}` → staff-api;
  - the session cookies' signing key, **generated by CDK** in Secrets Manager;
  - the environment's **monthly budget alarm** (about £5), counting only resources tagged `poised-env=<env>`.
- **`WebStack`** (`poised-<env>-web`):
  - an **Amplify Hosting** app with no repository connected (the web app is uploaded as a zip), branch `main`;
  - two rewrite rules, in this order: `/api/<*>` → the HTTP API (a reverse proxy, so the browser sees one origin and the cookies just work), then the SPA rule (every page's address → `/index.html`, but files and anything under `/assets/` are served as themselves, so a file missing after a deploy is a real 404);
  - the SSM parameter `<prefix>/app-url`: the web address, which the Lambdas read at cold start;
  - **security headers on every page and file** (S12): `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` (no framing), HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; **`Cache-Control: no-store` on pages** (Back after a sign-out on a shared computer shows nothing) and `immutable` on `/assets/`. A change to these headers shows only after the next web deployment (`make deploy-web`; the pipeline does it on every run).
- **`AuthStack`** (`poised-<env>-auth`, S12), deployed after WebStack because its callback addresses are the web address:
  - the **staff user pool** `poised-<env>-staff` (Cognito, **Essentials** plan: the cheapest with managed login; free to 10,000 monthly active users): the email is the username, **an authenticator app (TOTP) is required**, no self sign-up, password reset by email, Cognito's own email (`no-reply@verificationemail.com`, about 50 a day, no SES needed);
  - its **managed login** (Cognito's sign-in pages) at `https://poised-<env>-<hash>.auth.<region>.amazoncognito.com`, and the web app's client (code flow with PKCE, no secret; callback `<web address>/auth/callback`, sign-out back to `/login`);
  - the SSM parameters `<prefix>/cognito-user-pool-id`, `-client-id` and `-domain`, which the Lambdas read at cold start;
  - staff-api's permission to invite (`AdminCreateUser` on this pool only).
  - QA's pool is deleted with the stack; a real stage's is kept and has deletion protection.

The pipeline is one more stack, **`PipelineStack`** (`poised-pipeline`, in the account and region named by `PIPELINE` in `countries.py`): the CodePipeline `poised`, its GitHub connection `poised-github`, and two S3 buckets (the pipeline's artifacts, and the journeys' results), all deleted with the stack.

Nothing in the stacks names a region, domain or country default: those live only in `countries.py` (A-20), and `tests/` fails if a made-up second country's templates contain anything of the UK's.

| File | What it is |
| --- | --- |
| `countries.py` | Every environment: account, region, web address, time zone, locale, phone country, patient ID scheme, budget. (No dev login: on AWS staff always sign in with Cognito, S12.) Also `PIPELINE`: where the pipeline runs, and the repo and branch it follows. **The only place these are written.** |
| `app.py` | The CDK app: the pipeline stack, which holds one `PoisedStage` (ApiStack + WebStack) per entry. |
| `pipeline_stack.py` | The pipeline and its steps. |

## Before you start

- AWS CLI v2, Node 22+, Python 3.12+ and Go (the repo's versions). The CDK CLI is pinned in the `Makefile` (`npx aws-cdk@…`) and in `pipeline_stack.py` (a test checks they match), so don't install it globally.
- Sign in: `aws sso login --profile <profile>`.
- **Name the profile with `PROFILE=<profile>`** on every AWS target, e.g. `make deploy-qa PROFILE=<profile>`. It wins over `AWS_PROFILE` in `.env` (the Makefile loads `.env`, which would otherwise beat your shell's). Every script first prints the profile and account it will use, and stops before doing anything if the account isn't the entry's.
- `ENV` picks the entry in `countries.py`; it defaults to `uk-qa`.

## The manual steps (they can't be automated)

1. **Neon** (the database until the first customer): a free account, a project in **the country's own region** (for the UK, AWS London, `aws-eu-west-2`), with a database `sj`. Copy its **direct** connection string (not the pooled one: its host has no `-pooler`).
2. **Approve the GitHub connection**, once per account, after `make deploy-pipeline` (CloudFormation can only create it as Pending):
   1. Open the AWS console in the pipeline's region (`PIPELINE.region` in `countries.py`), signed in to the pipeline's account.
   2. Go to **Developer Tools → Settings → Connections** (or search the console for "Connections").
   3. Click **`poised-github`** (status **Pending**), then **Update pending connection**.
   4. A GitHub window opens. Sign in to GitHub as the repo's owner (`rlamba89`) if asked.
   5. Under **GitHub Apps**, click **Install a new app** (or pick the existing **AWS Connector for GitHub** installation if one is listed). On GitHub choose **Only select repositories → `rlamba89/poised`**, then **Install** (or **Save**).
   6. Back in the AWS window, click **Connect**. The status becomes **Available**.
   7. Start the first run: push to `master`, or in **CodePipeline → `poised`** click **Release change**.
3. **Click the two confirmation emails after the first deploy** (S17): SES's verification link, sent to the sender's address (until it's clicked, no email can be sent), and SNS's subscription confirmation, sent to the alert address (until it's clicked, no alarm email arrives).
4. **SES and SMS production access**, and a **sender ID's registration** (the UK requires one for sender IDs), before real patients: account paperwork that takes days. Until then the account is in both sandboxes: SES sends only to verified addresses (200 a day), SMS only to verified mobiles, with a $1 monthly spend limit (about 20 UK texts; raising it is a support request).

Everything else is below, and safe to run again.

## Setting up an account (or re-creating everything)

```sh
make aws-setup PROFILE=<profile> NEON_DATABASE_URL='<Neon direct URL>' ALERT_EMAIL='<your email>' EMAIL_FROM='<sender address>'
make deploy-pipeline PROFILE=<profile>
```

(`EMAIL_FROM` only for an entry that sends, which `uk-qa` does to its test recipients, S17.)

Then approve the GitHub connection (manual step 2 above) and push to `master`. The pipeline deploys QA, gives the seeded staff their test sign-ins, and runs the journeys against it. Its web address is the `AppUrl` output of `poised-uk-qa-web` (the E2E step's build also has it, as the environment variable `E2E_BASE_URL`; its log prints only the S3 address of the results). Staff sign in there with Cognito: see **Signing in on QA** below.

1. **`make aws-setup`** (`scripts/aws-setup.sh`), once per account and region; each step is skipped if done. If a value it needs is missing, it says so and stops before changing anything:
   1. **Poised's own CDK bootstrap**, apart from any other project's in the account:
      `cdk bootstrap aws://<account>/<region> --qualifier poised --toolkit-stack-name poised-cdk-toolkit`
   2. **The database URL**, as a SecureString (CloudFormation can't create those):
      `aws ssm put-parameter --name /sj/qa/database-url --type SecureString --value "$NEON_DATABASE_URL"`
   3. **The budget alarm's address**: `aws ssm put-parameter --name /sj/alert-email --type String --value "$ALERT_EMAIL"`
   4. **The sender's address**, for an entry that sends (S17): `aws ssm put-parameter --name /sj/qa/email-from --type String --value "$EMAIL_FROM"`
   5. **The `poised-env` cost tag**, so the budget can count by it:
      `aws ce update-cost-allocation-tags-status --cost-allocation-tags-status TagKey=poised-env,Status=Active`.
      Billing only learns a tag after a tagged resource has cost something, so on a new account this step says "not known yet": **run `make aws-setup` again a day after the first deploy.**
2. **`make deploy-pipeline`**: `cdk deploy pipeline`. Only the first time: after that the pipeline updates itself on each push (its **UpdatePipeline** stage).

## The pipeline

CodePipeline `poised` (V2: billed per minute while it runs, nothing when idle). Its stages, in order; a failed action stops the run there:

| Stage | Action | What it does |
| --- | --- | --- |
| **Source** | `rlamba89_poised` | Fetches the pushed commit of `PIPELINE.branch` through the `poised-github` connection. |
| **Build** | `Synth` | CodeBuild (arm64, Docker on). In order: `make lint test` (go vet, tsc, Go, Vitest, the CDK tests); starts Postgres in Docker and runs `make test-integration`; `npm run build -w apps/web`; `make synth` (builds the Lambdas, then `cdk synth`). **Any failing test stops the run here, before anything is deployed.** |
| **UpdatePipeline** | `SelfMutate` | Deploys `poised-pipeline` if the pipeline itself changed, then restarts the run. |
| **Assets** | `FileAssets` | Uploads the Lambdas' code to Poised's CDK bootstrap bucket. |
| **`uk-qa`** (one per entry in `countries.py`) | `poised-uk-qa-api` / `-web` Prepare + Deploy | CloudFormation change sets for ApiStack, then WebStack. |
| | `Database-and-web` | `scripts/db.sh` (goose up, then the seed, which is safe to run again) against the environment's database; **on QA only**, `scripts/qa-users.sh setup` (the seeded staff's test sign-ins, S12); then `scripts/deploy-web.sh` uploads the web app that Synth built. |
| | `E2E` | CodeBuild (Ubuntu: Playwright's WebKit needs it). `make e2e-setup e2e` against the environment's `AppUrl`: every journey, Chromium and WebKit (on QA, `scripts/e2e-users.sh` first fetches the test users' sign-ins into `e2e/.qa-users.json`; the journeys sign in through Cognito's managed login, and the few that need the dev login are skipped). **Fails the run if a journey fails.** Afterwards, passed or failed, it copies `e2e/test-results` (the JUnit report, and a trace of each failed journey) to the **E2eResults** bucket. |

**Finding the pipeline's pieces in the console** (the account is shared, and not everything is named `poised…`; the resources kept the old name when the product became Preopsis, 20 Oct):
- **CodeBuild projects are named by CDK:** `PipelineBuildSynthCdkBuildP-…` (Synth), `PipelineAssetsFileAsset…` (Assets), `PipelineukqaDatabaseandwebA-…` and `PipelineukqaE2E…` (one pair per environment), and `poised-selfupdate` (UpdatePipeline). Open them from the pipeline: an action's **View details**, then its link to CodeBuild. Or search **CodeBuild → Build projects** for `Pipeline`.
- **The Lambdas' log groups** are `poised-<env>-api-staffapilogs…`, `…patientapilogs…` and `…jobslogs…` (not `/aws/lambda/…`).
- The stacks, buckets, functions, Amplify app and connection are all named `poised…`.

## Signing in on QA (S12)

Nothing on QA works without credentials: staff sign in through Cognito's managed login (a password, then an authenticator app's code), the dev login doesn't exist there, and the testers' tools (`/qa/messages`, `/qa/jobs`, the sign-in limits reset, `/api/qa/client`) need a signed-in platform admin.

- **Test users** (`apps/api/cmd/qa-users`, QA only: it refuses any other stage). Every seeded staff account (Ada Admin, Alex Author, Bea Author, Cara Clinician, Max Multi, Sam Superadmin, Sue Super, Val Clinician) gets a sign-in with a known password and authenticator secret, kept only in the SSM SecureString `/sj/qa/test-users`. The pipeline runs it after each seed; by hand: `make qa-users PROFILE=<profile>`. Running it again keeps the passwords and secrets.
- **To sign in as one by hand:** open QA, **Sign in**, type the email, then
  - `make qa-password PROFILE=<profile> WHO='Cara Clinician'` copies the password to the clipboard (macOS; it's never printed), and
  - `make qa-code PROFILE=<profile> WHO='Cara Clinician'` prints the authenticator's current 6-digit code.
  Each code works once (wait for the next one if it's refused as used).
- **The journeys against QA from your machine:** `make e2e-users PROFILE=<profile>` (into the gitignored `e2e/.qa-users.json`), then `make e2e E2E_BASE_URL=<QA's address>`.
- **A superadmin with a real email:** `make aws-platform-admin PROFILE=<profile> EMAIL=you@example.org NAME="Your Name"`. A new account gets Cognito's invitation email (a temporary password, 7 days); the first sign-in asks for a new password and sets up the authenticator app.
- **Invitations and password resets** are emailed by Cognito itself (about 50 a day across the pool), so they reach any address even while SES is in the sandbox. A trust's real volume needs SES (pending.md).

## Texts and emails on QA (S17)

QA **captures every text and email** (`messaging="capture"`: the journeys and testers read them on `/qa/messages`), and because its entry has `qa_test_recipients=True`, it **also really sends the ones addressed to its test recipients**, and nobody else. The recipients are a comma-separated list in the SSM SecureString `/sj/qa/messaging-test-recipients`, never in the repo; SES's mailbox simulator (`…@simulator.amazonses.com`, AWS's own test addresses) is always allowed too. No parameter: QA really sends to no one.

- `make test-recipients PROFILE=<profile> TEST_RECIPIENTS='<+44… mobile>,<email>'` stores them and, for the sandbox, starts verifying each: SES emails an address a link (unless it's already an identity, e.g. the sender's), and a mobile gets a code by text.
- `make test-recipients-verify PROFILE=<profile> CODE=<the code>` verifies the mobile. `make test-recipients-status` shows how many are stored and the verifications' state (never the contacts).
- `make test-recipients-off PROFILE=<profile>` deletes the parameter. (The functions read it at cold start, so both targets also give the three functions a new description, which makes them start afresh at once.)
- **An undelivered message on QA:** create an episode for a patient whose email is `bounce@simulator.amazonses.com`: SES really sends it, it bounces, and within a minute the episode shows "Invite not delivered" and the alarm emails the alert address.
- **The jobs run by themselves** every 15 minutes on QA (`jobs_every_minutes`: each run wakes QA's Neon database, which a 5-minute schedule would keep awake past the free plan's hours); `/qa/jobs` shows the last run, and **Run jobs** runs them at once. Its clock offset applies to them as it does locally.

## Deploying

**Push to `master`.** That's all: the pipeline tests, deploys QA, migrates and seeds, deploys the web app, and runs the journeys. Watch it in **CodePipeline → `poised`**.

By hand, without the pipeline (e.g. the pipeline itself is broken), from your checkout:

| To | Run |
| --- | --- |
| Deploy a Go change | `make deploy-stacks PROFILE=<profile>` |
| Deploy a web change | `make deploy-web PROFILE=<profile>` |
| Run new migrations (and the seed) | `make aws-db PROFILE=<profile>` |
| The QA test users' sign-ins | `make qa-users PROFILE=<profile>` |
| Everything | `make deploy-qa PROFILE=<profile>` (stacks, migrations + seed, test users, web app) |
| Check the CDK without AWS | `make infra-test` or `make synth` |

**Changing the database URL:** `aws ssm put-parameter --name /sj/qa/database-url --type SecureString --overwrite --value '<new URL>'`. The Lambdas read it at cold start, so then run `make deploy-stacks` (or wait for the functions to be recycled).

## Rolling back

1. **The usual way: revert and push.** `git revert <bad commit>` then `git push`. The pipeline deploys the previous code, tested as usual.
2. **Faster, by hand:** check out the last good commit and run `make deploy-qa PROFILE=<profile>` (the stacks, migrate + seed, the web app). Then revert on `master` too, or the next push brings the bad commit back.
3. **Database migrations aren't rolled back by either.** goose only goes up in the pipeline. If a migration must be undone, do it by hand: `make aws-db` can't, so run `goose down` against the database (the URL is in SSM, see `scripts/db.sh`) from the commit that added it, before deploying the older code.
4. **Only the web app:** in **Amplify → `poised-uk-qa` → `main` → Deployments**, every earlier deployment is listed; there's no "redeploy this one" for manual deployments, so use 1 or 2.

## Reading a failed run

1. **CodePipeline → `poised`**: the failed stage is red. Click the failed action's **View details**, then **Link to execution details** (CodeBuild actions) to open its log.
2. **What each failure means:**
   - **Source** failed: the connection isn't **Available** (manual step 2), or the branch doesn't exist.
   - **Synth** failed: a test failed, or a build. **The log's very last error is a side effect:** `no matching base directory path found for infra/cdk.out` (the artifact upload fails because `cdk synth` never ran), so ignore it. About 20 lines above it, `Command did not exit successfully <command>` names the command that failed; scroll up from there to the first `FAIL` (Go), `FAIL`/`×` (Vitest) or `FAILED` (pytest). Run the same `make` target locally.
   - **SelfMutate** or a **Deploy** failed: a CloudFormation error. Open **CloudFormation → the stack → Events** for the reason. A deploy that failed rolls the stack back to the last good version by itself.
   - **Database-and-web** failed: a migration (goose prints the file), the seed, or the Amplify upload. Nothing after it ran, so the journeys didn't run against half-deployed code.
   - **E2E** failed: a journey failed against the deployed environment. The log's end lists them (`FAILED journeys/…`) and prints the S3 address of the results.
3. **The journeys' traces:** in **S3 → the `poised-pipeline-e2eresults…` bucket → `<env>/<build number>/`**: `junit.xml` and, for each failed journey, a folder with its traces. Download a `trace-N.zip` and open it with `e2e/.venv/bin/playwright show-trace <file>` (or drop it on https://trace.playwright.dev). [e2e/README.md](../e2e/README.md) explains reading a trace. Results are kept 30 days.
4. **To keep traces of a passing run** (e.g. to see what a journey did): in **CodeBuild → Build projects → the `…E2E…` project**, click **Start build with overrides**, add the environment variable `E2E_ARGS` = `--tracing=on`, set `E2E_BASE_URL` to the environment's address, and use the latest pipeline source. (It's a one-off build, outside the pipeline.)
5. **Re-run a failed run** without a push: **Retry failed actions** on the failed stage (e.g. after a flaky journey).

## Adding a country (the runbook)

A new country is **one entry in `countries.py` plus the steps below, never a code change** (A-20). The full list of what a country needs is in [saas-requirements.md §13](../docs/saas-requirements.md).

1. **Add the entry to `countries.py`**, e.g. `xx-qa`: the account, the country's AWS region, its IANA time zone, its `language-REGION` locale, its phone country (two letters), and its patient identifier scheme (a scheme in `apps/api/internal/nationalid`; add one there first if the country has its own). Run `make infra-test`: the entry is checked as it's made.
2. **Neon:** a project in the country's region (manual step 1), with a database `sj`.
3. **One-off set-up of the new region:** `make aws-setup ENV=xx-qa PROFILE=<profile> NEON_DATABASE_URL='<its URL>' ALERT_EMAIL='<email>'`. This bootstraps CDK in the region and stores its database URL. Run it again a day later for the cost tag.
4. **Later, when the country needs them:** its domain and DNS (`app_url`), SES and SMS production access and a sender ID in its region (manual step 4; `EMAIL_FROM` in `make aws-setup`, `sms_sender_id` in the entry), and its superadmin (`make platform-admin`, against its database).
5. **Push** the `countries.py` change to `master`. The pipeline updates itself (a new stage, `xx-qa`, after the existing ones), then deploys the new country, migrates and seeds its database, deploys its web app and runs the journeys against it.
   - A stage in a region other than the pipeline's also gets a small support stack, `poised-pipeline-support-<region>` (a bucket for copying artifacts there).
   - **The journeys' test data is the UK's** (a UK mobile, dates shown as "17 May 1980"), so in another country the journeys that use them (J3, J7, J8 and the patient-records journey) fail at those lines until they're written to read the country from `GET /api/config` (pending.md). Until then, run the others there, or give `E2E_ARGS` a `-k` filter.
6. Its web address is the new `poised-xx-qa-web` stack's `AppUrl`.

**Removing a country:** delete its entry and push (the pipeline stops deploying it), then `make destroy-stacks ENV=xx-qa PROFILE=<profile>` from a checkout that still has the entry. In the region, delete the SSM parameters (`/sj/<stage>/database-url`, `/sj/<stage>/email-from`, `/sj/<stage>/test-users` and `/sj/<stage>/messaging-test-recipients` on QA, `/sj/alert-email`), the SMS sandbox's verified destination numbers and any SES identities `make test-recipients` made, the `poised-pipeline-support-<region>` stack if there is one, and, if nothing else of Poised is there, the `poised-cdk-toolkit` stack and its retained `cdk-poised-assets-<account>-<region>` bucket (empty every version first).

**Proof, 14 Oct 2026 (S07):** a throwaway `us-qa` in `us-east-1` (America/New_York, en-US, US) took **about 10 minutes** from the new entry to J1–J5 passing: `make aws-setup` 1.5 minutes, `make deploy-qa` 5.5 minutes (stacks 72 s, migrations + seed 10 s, web upload), the journeys 2 minutes. It was then destroyed in about 5 minutes (the two stacks in about 1 minute; then the SSM parameters, the region's CDK bootstrap and its bucket, and the database). Details in [S07's build notes](../docs/sessions/S07-pipeline/build-notes.md).

## Moving to another AWS account (or re-creating everything)

Nothing but the steps above is needed, so everything can be deleted and re-created at any time.

1. **In the old account** (while `countries.py` still names it): `make destroy-pipeline PROFILE=<old profile>` (the pipeline, its connection and its buckets), then `make destroy-stacks PROFILE=<old profile>` for each environment. This deletes the Lambdas, the HTTP API, the Amplify app, the token secret (everyone is signed out), QA's staff user pool (the new account's pipeline makes new test users; a person's account in the database is tied to the new pool by their email at their next sign-in) and the budget. The Neon database isn't in AWS and is kept.
2. Optionally tidy the old account: `aws ssm delete-parameter --name /sj/qa/database-url`, the same for `/sj/alert-email`, `/sj/qa/email-from` and `/sj/qa/messaging-test-recipients`, `make test-recipients-off`'s verified mobiles (End User Messaging SMS → Verified destination numbers) and SES identities it made, and delete the `poised-cdk-toolkit` stack (empty its `cdk-poised-assets-…` bucket first).
3. In `countries.py`, change the entry's `account`, and `PIPELINE.account`.
4. **In the new account:** `make aws-setup …` (with `NEON_DATABASE_URL`, `ALERT_EMAIL` and `EMAIL_FROM`), then `make deploy-pipeline …`, approve the GitHub connection (manual step 2), push, and click the two confirmation emails (manual step 3). For real texts and emails on QA, `make test-recipients …` again (the sandbox's verifications are per account).
5. The web address changes (a new Amplify app gets a new `…amplifyapp.com` address) until there's a domain: give testers the new `AppUrl`.

## Notes

- **The branch:** the pipeline follows **`master`**, the GitHub repo's default branch (`PIPELINE.branch`). Plan F4 said `main`; nothing was renamed (S07). The Amplify app's own branch is also called `main`, which is unrelated: it's just where the zips are uploaded.
- **The client's address:** the patient sign-in rate limit counts by the browser's address. Behind Amplify's rewrite and API Gateway, the Lambda's connection is a proxy's, so `FORWARDED_HOPS` in `api_stack.py` (3, measured) tells the Go API which address in `X-Forwarded-For` is the browser's. `GET <AppUrl>/api/qa/client` (QA only) shows the address the API counts and the header it got.
- **Reserved concurrency** isn't set: a new account's Lambda concurrency limit can be as low as 10, which can't be split. Ask AWS to raise it before a real customer, then reserve some for patient-api.
- **Throttling:** API Gateway's defaults.
- **Cost when idle:** close to £0. Lambda, API Gateway, Amplify and EventBridge Scheduler are pay-per-use (the jobs schedule is about 8,600 runs a month, inside the free tiers); two CloudWatch alarms (within the free 10); SES and SMS cost per message; Secrets Manager is about $0.40 a month for the token secret; logs are small; Neon's free tier; CodePipeline V2 and CodeBuild are billed only while a run runs. The budget alarm emails at 80% of the month's budget, and when the forecast passes it.
- **Postgres in the pipeline** comes from ECR Public (`public.ecr.aws/docker/library/postgres`), not Docker Hub, whose anonymous pull limit shared build hosts can hit.
